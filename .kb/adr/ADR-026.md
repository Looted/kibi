## Context

Kibi previously let repositories relocate knowledge lanes and disable checks through `.kb/config.json`. That made enforcement a project setting instead of a product contract, so agents could compile a green health report without proving the stated intent.

## Decision

Kibi owns one canonical project contract:

- Authored knowledge lives under `.kb/{requirements,scenarios,tests,facts,adr,flags,events}` plus `.kb/symbols.yaml` and `.kb/symbol-coordinates.yaml`.
- `.kb/manifest.json` is Kibi-owned lifecycle metadata (schema version, semantic backfill). It is not a user configuration file.
- Check enforcement classes (`canonical`, `advisory`, `migration`) are owned by the installed Kibi version. `kibi check --rules` is an invocation-time diagnostic filter only.
- Leftover `.kb/config.json` and `documentation/` knowledge lanes are recognized only for one-way `kibi migrate --yes`.
- Executable e2e and benchmark harnesses stay outside knowledge lanes (`documentation/tests/e2e/`, `documentation/tests/benchmarks/`).
- Derived runtime trees (`.kb/branches`, `.kb/recovery`, `.kb/proof/runs`, `.kb/briefs`) are gitignored. Tracked proof-integration configuration lives at `.kb/proof/integrations.json` (Kibi-managed, bootstrap-authored; see ADR-027).

Humans configure product intent. They must not configure Kibi out of enforcing it.

## Consequences

- Fresh `kibi init` never writes `.kb/config.json` or user-configurable entity paths.
- Existing repositories must run `kibi migrate --yes` to move leftover `documentation/` knowledge into `.kb/`.
- Integration surfaces (MCP, OpenCode, VS Code, Cursor, Codex) treat `.kb/manifest.json` plus canonical lanes as the bootstrap contract.
