## Context

ADR-004 correctly required packed consumer tests, but its per-test npm prefix,
per-command SWI process, and fully serial execution assumptions predate the
journaled single-writer engine. Repeated CLI module loading and package installs
dominated test time, while detached fixture engines could remain alive until
the production ten-minute idle timeout and retain substantial memory.

## Decision

Keep packed tarballs as the consumer boundary, but prepare one immutable packed
installation per suite and share it across isolated test-file workers. Each
scenario still owns a fresh repository, home, cache, and engine runtime
directory. Run packed workers and curated root package batches with conservative
bounded concurrency rather than global serialization.

Reuse interactive Prolog or engine processes inside an explicit test isolation
boundary for ordinary behavior. Dedicated processes remain required where
startup, one-shot compatibility, crash recovery, or branch separation is the
behavior under test.

Every test harness assigns spawned engines to a private runtime directory and
terminates the exact PIDs recorded there before deleting fixture state. The
engine handles termination signals through the same save, journal fsync, and
socket cleanup path as an RPC stop. Unresponsive test-owned engines may be
killed after a bounded graceful wait.

Register CLI commands using a lightweight metadata projection that is
parity-tested against the authoritative operation catalog. Dynamically load
only the selected command and operation implementation.

## Consequences

Packed tests continue to catch missing tarball assets and installed-path bugs
without repeating installation work. Normal test behavior benefits from the
same long-lived architecture as production, while private runtime ownership
keeps concurrency deterministic and prevents daemon leakage. Lifecycle tests
still pay process startup costs intentionally. Catalog parity tests become a
required guard against drift introduced by lazy loading.
