Marketplace installs of the ZCode plugin now have working hooks. A ZCode marketplace install (GitHub source or local directory) copies the plugin directory as-is and never builds, so with the hook runner generated only into `dist/`, every lifecycle hook pointed at a file that was never there and silently failed to start; the plugin was only ever fully functional when the cache was hand-filled from a built checkout. The hook runner now ships as the repository-tracked `bin/hook-runner.mjs` bundle — the same distribution model the Claude, Codex and Cursor adapters already use — so `zcode plugins install kibi-zcode@kibi` from the `Looted/kibi` GitHub marketplace produces a working plugin out of the box, and the previously documented "GitHub-source installs are not supported" limitation is gone.

Technical summary: `hooks/hooks.json` points all five lifecycle hooks at `bin/hook-runner.mjs`; `scripts/build-hook-bundle.ts` regenerates the tracked bundle from `src/hook-runner.ts` with a `--check` drift mode wired into CI and publish workflows (`kibi-zcode check:hook-bundle`) next to the Claude, Codex and Cursor checks; a stale `dist/hook-runner.js` is removed by the build. The install-artifact test now models a marketplace copy from the tracked tree (no build output) and asserts every hooks.json target exists and runs in it, and a hooks.json test rejects hook commands whose targets only exist after a build; both cases joined the `TEST-zcode-kibi-plugin-v1` proof contract, and `kibi prove` passes with fresh receipts. README, `docs/install.md` and the ZCode package README now describe the marketplace install path; REQ-kibi-zcode-hooks-invoke-hook-runner records the rule with its scenario.
