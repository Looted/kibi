# Kibi SkillOpt check — 2026-11-12 (requirement size, ownership, sourced reasons)

## Outcome

The skills had no guidance on how large a requirement should be, which symbol owns it, or where a requirement's reason comes from. This change adds that guidance to kibi-usage, kibi-traceability, kibi-commit-review and kibi-decisions, plus two new SkillOpt families that measure it. Neither evaluated skill passes the no-regression rule. The runs show the guidance does no clear harm, but they do not prove it helps: the new cases are close to the baseline's ceiling or too noisy at two repeats.

| Run (development cohort, 2 repeats) | Baseline | Candidate |
| --- | ---: | ---: |
| kibi-traceability (14 cells per arm) | 91.43 (12/14) | 89.64 (11/14) |
| kibi-traceability `ownership-precision` (4 cells) | 85.00 | 85.00 |
| kibi-usage, first candidate (20 cells per arm) | 86.00 (13/20) | 79.75 (14/20) |
| kibi-usage, final candidate (20 cells per arm) | 79.25 (14/20) | 80.00 (13/20) |
| kibi-usage `requirement-quality`, final candidate (4 cells) | 53.75 | 27.50 (42.50 rescored) |

"Rescored" uses the corrected missing-reason detector in this change. In the logged writes, one candidate cell recorded "Reason beyond the naming review not stated", which the old detector missed. The other failing cell made up a reason ("keeps fixture families recognizable"), so it stays failed.

## New cases

- `kibi-traceability` `ownership-precision` (1 train / 2 development / 2 held-out):
  - `deciding_owner_link`: link only the function that decides a rule, not the wrappers that forward to it.
  - `link_keeps_requirement_size`: a new function next to a requirement that already has eight implementers decides a behavior of its own. Record a new requirement instead of linking it into the full one.
- `kibi-usage` `requirement-quality` (1 / 2 / 3):
  - `reason_without_source`: fill in a missing Context and record that no reason was stated, instead of making one up.
  - `reason_from_source`: copy a reason from the project notes and name its source.
  - `broad_requirement_split`: after approval, split a broad requirement by behavior, move each deciding symbol to its child, and close the parent.

## Observations

- `deciding_owner_link` scored 100 in every cell of both arms, so it does not separate the arms.
- In `link_keeps_requirement_size`, neither arm linked the new function into the full requirement. Both arms sometimes stopped before writing the new requirement.
- In `broad_requirement_split`, the first kibi-usage candidate made the agent read and grep `.kb/symbols.yaml` to find the parent's symbols (`direct_kb_access`, about 4M input tokens). The final candidate adds explicit split steps: list the links with `kb_graph` and `kb_query`, remove the parent's `implements` links with one `kb_delete`, relink each deciding symbol, and close the parent last. That removed the `.kb` reads (0 security failures for the candidate, 1 for the baseline), but neither arm reliably finished the relink. This case scores 0–75 in both arms.
- Some families moved in both directions between the two runs without any change to their text. They are noise at two repeats: fact-predicate-modeling 40–100, intent-consult 15–100, and one symbol-impact cell that skipped `kb_graph`.

## Method

Host: Claude Code CLI. Target claude-haiku-5-5 / low. The baseline is the skill text at the harness commit. Candidates were composed as body plus description replacements. Each run is one development-cohort evaluate with 2 repeats. There was no confirm or held-out run, and no significance is claimed.
