# Kibi SkillOpt campaign — 2026-10-20

## Outcome

Confirmed improvements without regression: **kibi-freshness**, **kibi-usage** and **kibi-traceability**. The freshness gain is the only large one (consistency-report 45 → 100, hard passes 0/20 → 4/20). The usage and traceability gains are small (+3.75 and +4.25 mean, one extra hard pass each) and sit within the variation seen between rounds. Canonical skills remain unchanged; the packaged files are review proposals.

## Scope and method

This campaign reruns the issue #339 core skills (kibi-usage, kibi-freshness, kibi-traceability) on the Claude Code host (`KIBI_SKILLOPT_HOST=claude-code`, Claude Code CLI 2.1.304). The optimizer profile is **claude-opus-5-5 / high** and the target profile is **claude-haiku-5-5 / low**. The target cap was 400 episodes. Bootstrap was out of scope.

Each development matrix evaluates the frozen candidates against the live baseline over five development families with two repetitions: ten cells per arm. Round 3 evaluated the round-1 and round-2 candidates of each skill together (thirty cells per skill). Confirmation used a fresh fixture root and two further repetitions of all three arms (thirty new cells per skill). Its combined aggregate holds the twenty round-3 and confirmation cells per arm. Two repetitions, not three, were used because three would have needed 135 cells and only 123 remained.

Scores are the campaign's existing 0–100 development scores; hard passes are the existing rubric decisions. Worst family is the minimum family mean, including ties. **KB-before-edit**, **search-before-edit** and **answer** follow the definitions in the [2026-10-04 report](2026-10-04-report.md): ordering is taken from the persisted normalized host events, skill list/load calls are excluded, and a cell without a recorded `file_change` counts its Kibi calls over the whole episode. This is a small repeated development comparison with no held-out run, statistical significance claim or production adoption.

Round 3, confirmation and packaging ran on source tree `3db32d604ff0134a666afe31383e73b6d82d9570`, which carries the harness fixes listed below. The evaluations record it as head `e7b463410ee8f2fe8f40fc4db9d6d89b437d40cc`; that commit was later re-authored as `c1379d33f` on this branch with the same tree.

## Harness corrections and excluded cohorts

Rounds 1 and 2 are **diagnostic only**. They spent 187 target episodes but are not evidence about the skills, for these reasons:

- **Seed fixtures failed their own validation.** The first round-1 evaluation of each skill stopped at fixture setup with `entity-context-missing` (9 cells per skill). Fixed in #516: seeded requirements carry a `## Context` section and the superseding requirement a `## Why this changed` section.
- **The target's Kibi engine had no SWI-Prolog.** The Claude Code target runs with `PATH` set to the `claude` directory plus `/usr/bin:/bin`, so a `swipl` installed elsewhere is invisible. Forty freshness and traceability cells ran without an engine. The documentation now states the requirement.
- **Fixture setup crashed for one artifact path.** Usage fixture setup at `kibi-usage/round-1/evaluate-N/fixture-readiness-<uuid>` crashed the Prolog process (`PL_scan_options`). It reproduced only at that path length; a different root name avoided it. The cause was not isolated.
- **Error-envelope calls made cells evidence conflicts.** A dry-run `kb_upsert` that fails validation is logged by the MCP server as a successful call with `result_status: error`, while the broker records it as failed. Every executable-coverage cell in one traceability run became `evidence-conflict` with score 0. `sealedDiagnostic` now excludes those rows.
- **The target never read the candidate.** Haiku called the Skill tool in 0 of 120 scored cells, and the 9 `kb_skills load` calls returned the shipped skill text, because the staged MCP runtime copied the shipped `dist/skills`. Baseline and candidate arms therefore ran on the same text, and round 1 and 2 deltas are noise. The target now gets the assembled variant of the skill under evaluation appended to its system prompt, and the staged runtime serves the assembled variants through `kb_skills`.

Round 1 and 2 candidates were still drafted by the optimizer from public feedback, and round 3 evaluated them unchanged after these fixes. No security failure was recorded in round 3 or confirmation; every cell finished as `completed` or `behavioral-failure`.

## Interpretation

Each candidate appends one paragraph to its skill body; frontmatter and resources are unchanged.

- **kibi-freshness** tells the agent to run the contradiction and coverage checks together, read the completeness information, and report incomplete analysis when a clause is unmodeled. Consistency-report rose from 45 to 100 with 4/4 hard passes. The other four families did not move.
- **kibi-usage** tells the agent to search by source location and query the governing requirement before the first edit, then follow a dry-run, write and read-back sequence for authorized mutations. Safe-mutation-direction rose from 27.5 to 40 and intent-consult from 81.25 to 87.5. KB-before-edit was already 4/4 for the cells that edited.
- **kibi-traceability** tells the agent to read preconditions and current requirements before writing a scenario that expects success, and to report infeasibility without writing when a requirement forbids an assumed value. Scenario-feasibility rose from 85 to 100 and executable-coverage from 21.25 to 27.5.

Fact-predicate-modeling and validation-recovery (usage), requirement-discovery and symbol-impact-granularity (traceability), and branch-status-classification, source-linked-impact and completion-outcome (freshness) stayed at 15 in every arm. No candidate reached those families.

Baseline scores varied between rounds (traceability baseline 44 in round 3, 42.25 combined). The usage and traceability gains are about the size of that variation, so treat them as weak evidence.
