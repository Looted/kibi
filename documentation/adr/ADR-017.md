## Context

### Problem

Relationships were previously authored in entity frontmatter (`links` field) and embedded in symbol manifest entries (`relationships` field). This design had several issues:

1. **Write Contention**: Relationships were defined as document authoring primitives, causing them to be scattered across multiple files
2. **Poor Separation of Concerns**: Relationships were co-located with entity concerns, making it difficult to validate relationship integrity as a whole
3. **Weak Traceability**: Without a canonical relationship graph, tracing relationship flows and detecting inconsistencies required querying all entity frontmatter
4. **Scalability Limitations**: File-based relationship authoring doesn't scale well for large, complex knowledge bases with many interconnections
5. **Race Conditions**: Concurrent modifications from multiple sources (CLI, MCP, manual edits) could create inconsistencies
6. **Storage Redundancy**: Duplicate relationship definitions were possible (same type/from/to in multiple files)
7. **Migration Complexity**: Moving from document-embedded relationships to canonical storage would require careful migration to avoid data loss

### Decision

Implement canonical relationship shards as the single source of truth for relationships:

1. **Storage Format**: Shard YAML files in `.kb/relationships/` directory, each named by the source entity's first 2 hex characters of its SHA-256 hash
   - Each shard contains a `relationships` array with typed relationship records
   - Records include: `id`, `type`, `from`, `to`, `created_at`, `created_by`, `source`, `confidence`
   - Shard files are deterministic and human-readable

2. **Relationship IDs**: Stable, content-addressable IDs derived as `rel-` + first 12 hex chars of SHA-256(`type|from|to`)
   - This ensures relationships are unique and referenceable

3. **Metadata Preservation**: All relationship metadata (timestamps, provenance, confidence scores) is preserved from the canonical source
   - No loss of traceability or audit information during storage layer migration

4. **Write Semantics**: Relationships are written by explicit tools (CLI sync, MCP upsert/delete) only
   - No tool writes directly to shard files as a side effect
   - Authoring tools are removed from entity extractors and symbol manifest writers

5. **Read Semantics**: Relationships are read and validated against entity ID sets before being asserted into the knowledge base
   - This ensures referential integrity (no dangling references to non-existent entities)

6. **Deduplication Prevention**: Shard-based storage with stable IDs prevents duplicate relationships
   - The same `implements REQ-xxx` comment cannot create duplicate relationships because IDs are derived deterministically

7. **Scalability**: Shard distribution is naturally scalable
   - Adding more relationships doesn't require changing entity files
   - Each shard is independent, enabling concurrent operations

8. **Migration Path**: Clear canonical source makes migration straightforward
   - One-time script can extract, validate, rewrite, and rebuild caches
   - Post-migration, the new canonical state is self-validating

### Consequences

1. **Positive**:
   - Single source of truth for relationships improves data integrity and traceability
   - Referential integrity checks become simpler and more robust
   - Relationship metadata is preserved and queryable
   - Storage format is human-readable and version-controllable

2. **Negative**:
   - Requires migration of existing knowledge bases
   - CLI/MCP tools must be updated to canonical storage
   - Documentation and examples must be updated

3. **Neutral**:
   - Performance impact: Minimal (shard reads are I/O-bound but async-friendly)
   - Developer experience: New workflow (author in canonical files vs embedded frontmatter)

## Alternatives Considered

1. **Embedded relationships with metadata**:
   - Keep links in frontmatter as pure strings, generate canonical shard rows with full metadata
   - Advantage: Simpler to implement for smaller projects
   - Disadvantage: Still co-located with entity concerns, weak traceability

2. **External relationship graph (RDF) with triple stores**:
   - Leverage existing triplestore implementation
   - Disadvantage: Significant complexity, RDF overhead
   - Advantage: Industry-standard approach for graph databases
   - Disadvantage: Doesn't use file-based storage, harder to reason about for this codebase

3. **Document database**:
   - Use a proper graph database (PostgreSQL, Neo4j)
   - Advantage: Native relationship querying, ACID compliance, proven scalability
   - Disadvantage: Requires significant infrastructure changes, moves away from file-based simplicity
