## Context

The old upsert executor awaited RDF mutation, entity audit, relationship audit, and snapshot save as separate Prolog calls. Bun one-shot execution could auto-save after the first call, while a long-lived SWI-Prolog runtime retained an exclusive `audit.log` lock under persistency's default `sync(flush)` mode. A blocked audit call therefore could leave durable RDF without a complete audit trail and could outlive the caller's synchronous timeout.

## Decision

Use `sync(close)` for the persistent audit database and expose one internal `kb_commit_upsert/5` predicate. The predicate acquires the branch lock, verifies the attached snapshot, probes the existing audit journal without waiting, performs RDF mutation and contradiction checks, appends all audit rows, and saves one snapshot. Stage markers and runtime identity diagnostics are emitted to stderr. The CLI submits only this goal and consumes its returned `created`/`updated` kind.

Manage one-shot SWI-Prolog children asynchronously in detached process groups. On timeout or bounded-output overflow, send `TERM`, escalate to `KILL` after the grace period, await process close, and remove the child from the runtime's tracked set. Older runtimes are never terminated automatically; their retained audit lock produces an actionable restart message.

## Consequences

Successful upserts publish one coherent RDF/audit snapshot and current runtimes release the audit lock after each append. Stale snapshots and old lock holders fail before RDF mutation, and timeout messages identify the last stage without logging entity payloads. Existing KB files and journal syntax remain compatible; operators must restart stale MCP/CLI sessions after upgrading.
