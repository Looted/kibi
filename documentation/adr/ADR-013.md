## Context

Kibi is distributed as a monorepo with multiple packages that have different release targets and consumption models. There was ambiguity about which packages are published to npm versus bundled or published elsewhere, leading to documentation drift.

## Decision

**Decision**: Establish a clear package matrix where `kibi-core`, `kibi-cli`, `kibi-mcp`, and `kibi-opencode` are release-managed npm packages with independent versioning, while `kibi-vscode` is published exclusively to the VS Code Marketplace.

### Package Matrix

| Package | Directory | npm Name | Published To | Current Version | Dependencies |
|---------|-----------|----------|--------------|-----------------|--------------|
| kibi-core | `packages/core/` | `kibi-core` | npm | 0.5.0 | None |
| kibi-cli | `packages/cli/` | `kibi-cli` | npm | 0.6.0 | `kibi-core: ^0.5.0` |
| kibi-mcp | `packages/mcp/` | `kibi-mcp` | npm | 0.7.0 | `kibi-core: ^0.5.0`, `kibi-cli: ^0.6.0` |
| kibi-opencode | `packages/opencode/` | `kibi-opencode` | npm | 0.7.0 | `@opencode-ai/plugin: ^1.2.26` |
| kibi-vscode | `packages/vscode/` | N/A | VS Code Marketplace | N/A | N/A |

### Versioning Model

- **Independent versioning**: Each npm package maintains its own version in `package.json`
- **Changesets-style selective publishing**: The publish workflow (`.github/workflows/publish.yml` and `scripts/publish-selective.sh`) only publishes packages whose local version does not yet exist on the npm registry
- **Semver ranges**: Packages declare dependencies using caret (`^`) ranges to allow compatible updates
- **No workspace protocol**: Published packages use concrete version ranges instead of `workspace:*` to ensure they work when installed outside the monorepo

### Release Process
1. **Work and Changesets**: Changes are made on `develop`. Changesets are created immediately to record intent.
2. **Versioning on Develop**: Version bumps are applied on `develop` using `bun run version-packages`. This updates `package.json` and `CHANGELOG.md` files.
3. **Merge to Master**: `develop` is merged to `master` after versioning is complete.
4. **Master CI Publishing**: The `master` CI workflow builds and publishes packages whose versions are not yet on npm. `master` remains publish-only and does not create new commits.

3. **Provenance**: All npm publishes include `--provenance` for supply chain security

## Rationale

- **kibi-core as independent package**: While kibi-core contains only Prolog files (no compiled JS), publishing it separately allows:
  - Proper dependency declaration in kibi-cli and kibi-mcp
  - Independent versioning of the core graph logic
  - Potential external consumption by other tools
  
- **Separate npm packages vs bundling**: Keeping core separate (rather than bundling into cli/mcp) maintains:
  - Clear separation of concerns
  - Smaller package sizes for cli/mcp
  - Ability to patch core independently

- **opencode published, but locally dogfooded in this repo**: `kibi-opencode` is a normal npm package for external consumers, but this repository's own OpenCode setup intentionally loads local `kibi-mcp` and `kibi-opencode` build artifacts during development
- **vscode excluded from npm**: The VS Code extension has different distribution mechanics and marketplace requirements

## Consequences

### Positive
- Clear contract: README, workflows, scripts, and package.json all agree on the package matrix
- Selective publishing reduces unnecessary releases
- Tarball verification catches packaging errors before publish
- Independent versioning allows targeted updates
- The dogfood setup exercises local `kibi-mcp` and `kibi-opencode` artifacts before release

### Negative
- Must coordinate version bumps across four packages when shared behavior changes
- Local dogfood use of `kibi-mcp` and `kibi-opencode` means version bumps require a fresh `bun run build` before OpenCode testing in this repo
- Release process requires all four npm packages to build and pack even if only one changes
